# 双模式设计：自动识别 + 手动映射

> 本文扩展 `方案-聊天记录查看器.md` 里的 recipe（配方）机制，把它落成可实现的规格。
> 用户的想法（原始表述）：「针对 json 的两个模式：1. 自动识别；2. 根据 json 的 key-value 格式手动规定什么是 key 什么是 value，并决定显示哪些内容之类的」。

## 0. 一句话

两个模式是**同一套 Recipe 引擎的两个入口**：自动模式把配方猜出来，手动模式把配方写出来，
两者落盘成同一种 JSON、互相流转。手动模式的产出反过来喂给自动模式 —— 用户每配一次，这类文件以后就自动认得了。

## 1. 为什么必须有两个模式

| | 自动模式 | 手动模式 |
|---|---|---|
| 覆盖 | 主流导出格式（ChatGPT/Claude/SillyTavern/微信/WhatsApp...） | 长尾：自研导出、Excel 转 JSON、内网工具、改过字段名、单会话 vs 多会话 vs 树 |
| 用户成本 | 0 | 需要 3~6 次点选或写几条路径 |
| 风险 | 猜错且用户不知道为什么错 | 用户配不出来（不知道 JSONPath） |

只做自动 = 覆盖不全，且失败即死路；只做手动 = 没人用。
**自动是主路径，手动是兜底，兜底的结果变成自动的知识。** 这是与 Pine 一类「自动但黑盒」产品最大的差异点。

## 2. 统一出口：Recipe 的五个部分

```json
{
  "id": "chatgpt-export",
  "version": 2,
  "detect":  { "kind": "JSON", "allOf": ["mapping", "current_node"], "weights": { "mapping": 2, "current_node": 3 } },
  "locate":  { "conversations": "$", "conversation": "$[*]", "messages": "$.mapping" },
  "extract": { "title": "$.title", "time": "$.create_time",
               "msgId": "$.id", "parent": "$.parent", "leaf": "$.current_node",
               "role": "$.message.author.role", "text": "$.message.content.parts[0]" },
  "assemble": { "order": "tree-from-leaf", "dedupe": "msgId" },
  "display": { "fields": ["time", "role", "text"], "roleMap": { "assistant": "AI", "user": "我" },
               "filters": ["system", "toolCalls", "empty"], "mergeConsecutiveSameRole": true }
}
```

- `detect` 决定「这个文件归哪个配方管」（自动模式的打分依据）
- `locate` + `extract` + `assemble` 是**识别层**：数据在哪、字段怎么取、怎么拼成有序会话
- `display` 是**展示层**：显示什么、怎么显示 —— 这一层独立的好处是同一份数据能有多套视图
  （「只看对话」/「带思考过程」/「只看我发的」），不用复制 recipe

## 3. JSON 手动映射的三种交互粒度

同一个 recipe，三种编辑方式，互为替代：

1. **点选式（默认，小白）**：上半屏原文、下半屏渲染预览。用户点一句话「这是消息」→ 记录路径；
   再点其中一段「这是正文」→ 记录相对路径。每点一次，预览实时重排。
2. **表单式（推荐主用）**：先从自动推断拿 Top-3 候选预填，用户只改错的下拉框：
   会话数组 / 消息数组 / 角色字段 / 正文字段 / 时间字段 / 父子关系。
3. **表达式式（高级）**：直接写 JSONPath，用于导入导出、社区分享、批量修。

三者本质相同 —— 点选和表单就是 JSONPath 的可视化编辑器，产出同一个 `recipe.json`。

## 4. 路径要解决的真实坑（不写清楚就做不出来）

1. **消息容器经常不是数组**。ChatGPT 的 `mapping` 是 dict；Claude 的是数组。所以取值语义必须支持两种：
   数组 `[*]` 与对象取值 `.*`（values），否则 ChatGPT 系永远绑不上。
2. **树形导出必须能指定父子关系**。存储顺序 ≠ 显示顺序。手动模式若只允许「选消息数组」，
   用户会得到乱序 + 重复分支。所以配方里要有 `parent` / `leaf` 两个可选路径，`assemble.order = tree-from-leaf`。
   这是现有文档里已定的算法（从叶子回溯再 reverse），这里把它变成可配置项。
3. **相对路径优先**：先绑「消息集合」，其余字段都相对单条消息，换同格式的新文件即复用。
4. **每条路径即时校验**：绑定时在原文采样，显示「命中 N 个值 / 第一个值前 40 字」。0 命中标红，
   命中数 > 1 且期望单值则提示「你可能选到了数组，请再点深一层」。
5. **字段别名**：`role` / `sender` / `author` / `from` / `is_user`；`text` / `content` / `message` / `parts`。
   内置别名表 + 用户覆盖，减少手动量。

## 5. 「决定显示哪些内容」的清单（display 层）

- 字段可见性：时间 / 角色 / 正文 / 附件 / 引用
- 角色改写：`assistant → AI`、`human → 我`
- 过滤：系统消息、工具调用（tool/function）、思考过程（reasoning/thinking）、空消息、重复分支
- 合并：连续同角色合并（IM 风格 vs 文档风格两种渲染）
- 排序：时间正序 / 倒序 / 树形分支折叠

这些全部只作用于 IR，绝不回头改解析结果 —— 保证「同一个文件，换个看法不用重扫」。

## 6. 类比到其他格式（同一套心智模型）

| 格式 | 自动 | 手动映射 = |
|---|---|---|
| txt | 6 种内置聊天行格式 | 行正则 + 字段槽位（time/name/text）+ 续行规则 + 系统消息正则 |
| csv | 列名关键词 | 列 → 字段的下拉映射（比 JSON 更简单） |
| zip | 分片/附件识别 | 选入口文件；内部再递归走同一套 |
| html | 常见导出模板 | CSS selector 映射（二期） |

## 7. 失败路径（体验的核心）

自动置信度低于阈值时，**不弹「无法识别」**，而是：

「看起来是一组消息（检测到 12 个对象含 role/content）。要手动指定吗？」→ 预填 Top-3 候选 → 用户改两三下 → 预览正确
→ 弹「保存为配方，下次自动使用」→ 写入本地配方库，`detect` 打分时**用户配方优先于内置配方**，可启用/禁用。

配方可命名、可导出为 `.chatrecipe.json`、可分享 —— 这是文档里说的护城河：
用户越多，覆盖的格式越多，后来者越难追。

## 8. 实现顺序（MVP 到完整）

1. **CLI：`--bind recipe.json`** —— 手动映射真正跑通：读 recipe，输出整齐的会话文本/JSON。
   这一步验证引擎，不碰 UI。（当前 Sniffer 的下一步）
2. **CLI：`--infer`** —— 输出 Top-3 候选绑定 + 命中统计，作为 UI 预填的数据源。
3. **Android：IR + 渲染层** —— 先只支持加载现成 recipe 文件，不做编辑器（能看就有价值）。
4. **Android：点选式编辑器 + 配方管理 + 分享**。

## 9. 与现有代码的接口

`Sniffer.java` 已经产出 `kind` / `encoding` / `format` / `notes` —— 正好是 `detect` 段的前半部分。
bind 引擎接在它后面：`detect` 命中 → 取对应的 `locate/extract` → 解析（大文件用流式）→ IR → 渲染。
手动模式产出的 recipe 与内置 recipe 同结构，所以两条路走同一个执行器。

## 10. 原型落地情况（prototype/）

Web 原型已可点：`prototype/index.html` 双击即开（file://，无依赖、无联网），默认加载 ChatGPT 样本。

- 自动模式：候选卡片带分数与路径，点卡片即换绑定；ChatGPT 的 `mapping` dict、Claude、SillyTavern JSONL、WhatsApp txt 四个真实样本都能出正确气泡。
- 手动模式：会话/消息/角色/正文/时间/消息 ID/父节点/标题/叶子/排序 十个字段，下拉里直接显示本文件中的命中样本值，改任一项预览实时刷新。
- 配方：右侧底部实时生成五段 JSON，可复制/下载 —— 这就是 Android 端要存的格式，与内置配方同结构。
- 已验证：`node test.js` 36 条断言全过；CDP 在真实 Chromium 中检查三栏布局无横向溢出、切样本无状态残留、无运行时报错。

这一步确证了三件事，可直接指导 Android 实现：

1. `locate/extract` 用「相对当前节点的路径 + 实时采样预览」就足够表达当前所有真实导出格式，不需要一上来就做 JSONPath 全语法。
2. 树形还原必须在**装配阶段**做（leaf 回溯），而不是在路径解析阶段 —— 否则旁支会重复进入。
3. 手动模式的表单字段顺序，就是 Android 点选式编辑器的引导顺序；两者共用同一份 recipe schema，无第二套数据模型。

细节与文件清单见 `prototype/README.md`。

## 11. 文本侧：把标签结构切成块（用户 m00225 的需求落地）

JSON 侧解决「噪音字段」，文本侧是另一个问题：导出成 txt / 半 HTML 的聊天记录里，**辅助信息与对话混在一条流里**
（`<div class="status">…</div>`、`<details><summary>内心</summary>…</details>`、`【状态】…`）。
不分块，读起来就是一堆状态栏插在剧情中间；直接丢又丢失了信息。

做法与 JSON 侧同构，仍是五段 recipe，只是字段换了：

| 段 | JSON 侧 | 文本侧 |
| --- | --- | --- |
| detect | 魔数 / 编码 / JSON 结构打分 | 编码 + 标签统计（有 `<div class="mes">`？有 `<details>`？只有 `名字:`？） |
| locate | 会话路径 / 消息路径 | 容器签名（`div.mes`）+ 对话行规则 |
| extract | role / text / time / parent | 容器内 `name / mes_text / time` 类名 + 行规则命名组 |
| assemble | 数组顺序 / leaf 回溯 | 原文顺序，块 attach 到所属消息或独立成项 |
| display | 字段可见性 / 过滤系统 | 块类别可见性 + 折叠 + 徽章配色 |

### 11.1 块是什么

「相同标签之间的内容」= 一个块（block）。块有类别（状态栏 / 内心 / 摘要 / 系统 / OOC / 选项 / 场景 / 装饰 / 折叠块），
类别决定它在气泡里的徽章与配色，也决定默认收起。块可以嵌套（`<details>` 里再有 `<div class="stat">`）。

关键判断：**块不是丢弃，是降级为可展开的盒子**。用户能一眼扫过（收起），需要时再展开（不改原文一个字）。

### 11.2 两个模式如何对应

- 自动：软件自己猜容器 + 分类。猜错的代价低 —— 类别只是盒子徽章，不影响对话本身。
- 手动：软件先给出「识别到的块」清单（签名 × 次数 × 首行样本），用户只需要改下拉：
  这是状态栏 / 这是内心 / 忽略不显示；以及选「块跟随所属消息」还是「独立插在对话之间」。
  改一下立刻重排预览 —— 与 JSON 侧「改路径立刻刷新」是同一个交互。

手动产物同样写回 recipe 的 `text` 段：

```json
{
  "detect": { "kind": "TEXT", "format": "html blocks (div.mes)" },
  "text": {
    "containers": ["div.mes"],
    "blocks": { "details.think": "thought", "div.stat": "status", "pseudo:状态": "ui" },
    "attach": "inline",
    "rule": "auto"
  },
  "display": { "showSystem": true, "fields": ["name", "time", "text"] }
}
```

`blocks` 的键是「签名」——标签 + class 排序 + id（`div.mes`、`details.think`），伪标签则是 `pseudo:状态`。
这就是 Android 端要存的文本配方；用户配方优先于内置词表，与 JSON 侧同一条规则。

### 11.3 实现要点（Android 移植时照此）

1. **标签栈扫描，不用 DOM / 不引 HTML 解析库**：单遍正则 + 栈，容错未闭合与多余闭合，顺带产出诊断数字
   （「3 处未闭合」比「解析失败」有用）。`<style>`/`<script>` 整段跳过。MARKERS（`<START>` 之类）不建栈。
2. **容器判定要看统计而不是名字**：同签名出现 ≥2 次、多数有子元素、平均长度合理、语义像对话 —— 四条同时满足才算容器；
   被容器包住的内层容器剔除（`div.mes` 里的 `div.mes_header` 不是消息）。
3. **容器内部抽字段**：深度优先找第一个匹配 `name|speaker|author|who|char|sender` 的元素当名字，
   `text|content|body|message|bubble|speech` 当正文，`time|date|timestamp` 当时间；头部元信息（`header|meta|avatar`）不参与块检测，
   否则时间戳会被误判成「场景」块。
4. **块分类靠双语词表打分**，不靠正则穷举：标签名 + class + `<summary>` 文本一起进 haystack，得分最高者胜。
   实测 `details.think` 的 `summary` 写「内心」也能纠正成内心块。
5. **伪标签必须与行规则互斥且有终止条件**：`【状态】` 之后的内容延续到「空行 / 下一条 `名字:` 行 / 下一个伪标签」为止，
   否则状态栏会吞掉后续对话（这个坑在原型里踩过：`<START>` 未特殊处理时吞了全文，0 条消息）。
6. **块的位置**：默认 `inline`（挂在刚出现的那条消息里，保持原文顺序，符合酒馆状态栏属于 AI 这条消息的直觉）；
   手动模式可切 `standalone`（独立插在对话之间）。块与文本用 `parts` 数组表达，渲染层按顺序遍历，不需要两套模型。
7. **正文清洗**：块文本要从消息正文里扣掉，名字/时间也要扣掉（否则气泡里出现「{{char}} 22:40 记得…」）。
   容器的正文优先取 `mes_text` 这类元素，取不到才回退到整块文本再扣。

### 11.4 原型验证结果

- `node test-text.js` 38 条断言全过：容器只剩最外层、名字/正文/时间抽取、`details`→内心且 summary 不重复、
  `div.stat`→状态栏、内联 parts 顺序、中文四类伪标签、手动改类别（含容器内块）、关闭容器、standalone、
  畸形标签容错、`style/script` 跳过、纯文本不崩。
- CDP 实测 1600×1000：酒馆样本 4 条消息 3 个块全部内联在气泡里；中文样本 5 条消息 5 个块，场景块独立排最前；
  手动模式把 `pseudo:*` 改成「忽略」后块数 5→4；切回 ChatGPT 样本无状态残留；无横向溢出。

这一节确证的是：**文本侧的「分块」与 JSON 侧的「字段映射」可以共用同一套 recipe 外壳**，
差别只在 locate/extract 的实现 —— 所以 Android 端不需要为 txt 单独做一套界面，只需要多一个「块清单」面板。

### 11.5 气泡左右：角色与布局分家

用户反馈（原型初体验）：用户侧消息应该在左边，或至少允许自定义哪类消息在左/右。

实现的关键是把两件事拆开：

- **配色由角色决定**：我 / AI / 系统 / 其他人各有气泡底色与名字颜色，不随布局变。
- **左右由设置决定**：`display.align` 把角色映射到 left / right / center，默认「我」靠左、AI 靠右、系统居中。

代码上就是 `msg me side-left` 两个独立类：`colorClass(role)` 出配色，`sideOf(role)` 出对齐。
改布局只动 `side-*`，不影响语义配色，也不会把「我」错认成别人。

对 Android 的价值不在像素，而在**默认值必须对**：阅读式导出里用户提问在左、AI 在右，
先给对标的方向，再给一个开关。很多人导出记录是为了重读自己与 AI 的对话，方向反了会一直别扭。

验证（`prototype/verify-align.js`，1600×1000）：酒馆样本「我」x 偏移 0（贴左）、AI 距右 0（贴右）；
手动把「我」改成靠右后四条消息全部贴右；ChatGPT 样本同样左右交替；配方 `display.align` 同步更新；无横向溢出。
